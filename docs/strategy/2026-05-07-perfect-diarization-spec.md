# Perfect Diarization Spec

Date: 2026-05-07

## Goal

Build polyvoice into the strongest deployable diarization engine for Rust: accuracy competitive with pyannote-class systems, simpler deployment than Python/PyTorch stacks, and better reproducibility than current OSS competitors.

"Perfect diarization" does not mean zero DER on arbitrary real audio. It means the system exposes and attacks every major diarization failure mode:

- missed speech
- false alarms
- speaker confusion
- overlapped speech
- speaker-count errors
- label switching and fragmentation
- unstable streaming speaker identity
- bad word-level speaker assignment
- noisy/far-field/many-speaker degradation

## North-Star Metrics

All public claims must be generated by checked-in commands and saved result artifacts.

| Metric | Baseline target | Winning target | Notes |
|---|---:|---:|---|
| VoxConverse test DER | <= 11.5% | <= 8.5% | Must report miss/FA/confusion separately. |
| AMI Mix-Headset DER | <= 18.0% | <= 12.0% | Include 0.25s collar and no-collar variants. |
| AMI far-field/array DER | <= 22.0% | <= 16.0% | This is where current polyvoice likely needs the most work. |
| DIHARD-like DER | <= strong OSS baseline | best open reproducible Rust result | Use when dataset setup is available. |
| Speaker count within +/-1 | >= 85% | >= 93% | Report by speaker-count buckets. |
| Overlap F1 | >= pyannote community-class | better than pyannote community-class | Requires neural overlap-aware output. |
| CPU throughput | >= 8x realtime | >= 15x realtime | On documented CPU, with model hash. |
| GPU/CoreML throughput | >= 50x realtime | >= 100x realtime | Optional features only. |
| Streaming latency | <= 1.0s usable mode | <= 500ms low-latency mode | Report DER/latency tradeoff. |

## Design Principles

1. Reproducibility before marketing.
2. Model families are adapters, not hardcoded pipeline assumptions.
3. Accuracy improvements must preserve Rust deployability.
4. Overlap is a first-class output, not post-hoc interval intersection.
5. Speaker identity should be stateful when the user asks for continuity, but anonymous when they ask for privacy.
6. Every public API must encode invariants and avoid invalid states.

## Target Architecture

```text
[Audio Input: wav/pcm/stream]
          |
          v
[Preprocess: resample, levels] ---> [Benchmark Recorder: timings, hashes]
          |
          v
[Segmentation: VAD or neural] ---> [Powerset Decoder: overlap-aware frames]
          |                                      |
          v                                      v
[Embeddings: model zoo] <-------- [Overlap-aware weights, cannot-link evidence]
          |
          v
[Scoring: cosine/PLDA/calib] ---> [Speaker Count: BIC/eigengap/PLDA]
          |                                      |
          v                                      v
[Clustering: AHC/spectral/VBx] -> [Resegmentation: HMM/VBx smoothing]
          |                                      |
          v                                      v
[DiarizationResultV2: turns, overlap turns, frame scores, confidences,
 speaker-count diagnostics, word assignment]
```

## Core Components

### 1. Evaluation Harness

Add a benchmark harness that treats datasets, model files, configs, and outputs as reproducible artifacts.

Required capabilities:

- Dataset manifests for AMI, VoxConverse, and later DIHARD/CALLHOME-like corpora.
- Unified metrics: DER, JER, miss, false alarm, confusion, overlap F1, speaker-count exact and within +/-1, real-time factor.
- Runner abstraction so polyvoice, pyannote, speakrs, diarize, sherpa-onnx, and parakeet-rs can be compared under the same collar and overlap policy.
- JSON and Markdown result outputs with model hashes, crate versions, CPU/GPU info, config, and git SHA.
- One-command smoke benchmark and full benchmark modes.

Acceptance criteria:

- `polyvoice-bench` can emit machine-readable result JSON.
- README benchmark tables are generated from saved result JSON, not hand-edited.
- `src/der.rs` is the single source of DER truth; duplicate benchmark-only DER code is removed.

### 2. Neural Segmentation and Powerset Decoding

Add a segmentation abstraction separate from VAD.

Required traits:

```rust
pub trait SegmentationModel {
    fn segment(&mut self, samples: &[f32], config: &SegmentationConfig)
        -> Result<SegmentationOutput, SegmentationError>;
}

pub struct SegmentationOutput {
    pub frame_step: Seconds,
    pub frame_duration: Seconds,
    pub speaker_activity: FrameSpeakerMatrix,
    pub overlap_probability: Option<Vec<Confidence>>,
}
```

Required behavior:

- Support existing Silero VAD as a lightweight segmentation backend.
- Add a neural pyannote/community-style ONNX segmentation backend when model licensing and export are clear.
- Implement powerset decode for multi-speaker local speaker states.
- Implement overlap-add aggregation and binarization with tunable onset/offset thresholds.
- Preserve a pure Rust post-processing path.

Acceptance criteria:

- Overlap regions can be inferred from model posteriors, not only from already-labeled segments.
- Frame-level activity can represent zero, one, or multiple speakers.
- Synthetic overlap tests prove two simultaneous speakers survive into output.

### 3. Model Zoo and Embedding Backends

The current WeSpeaker/ECAPA path should become a model-family abstraction.

Candidate families:

- WeSpeaker ResNet34/ResNet34-LM
- ECAPA-TDNN
- TitaNet
- WavLM/SSL embeddings if export is practical
- ERes2Net/CAMPPlus from WeSpeaker if ONNX export is practical
- Sortformer as a separate end-to-end diarization backend

Required metadata:

- model name
- source URL
- model hash
- license
- expected sample rate
- input/output tensor schema
- embedding dimension
- benchmark compatibility

Acceptance criteria:

- Model download/cache code refuses unknown hashes by default.
- CLI can print `polyvoice models list` and `polyvoice models info`.
- Benchmarks record model metadata automatically.

### 4. Scoring and Speaker Count

Current cosine thresholding is insufficient for the winning target.

Required scoring backends:

- cosine scoring baseline
- calibrated cosine with score normalization
- PLDA scoring
- optional AS-Norm / quality-aware score calibration

Required speaker-count estimators:

- known `num_speakers`
- min/max speaker range
- eigengap and spectral criteria
- BIC/silhouette-style estimator
- PLDA likelihood-based estimator when PLDA is available
- diagnostics explaining why the count was selected

Acceptance criteria:

- Speaker-count accuracy is benchmarked separately from DER.
- Many-speaker files are bucketed and reported.
- The result object includes count confidence/diagnostics.

### 5. Clustering and Resegmentation

Current AHC/spectral/k-means should remain, but the winning pipeline needs VBx-style resegmentation.

Required backends:

- AHC baseline
- spectral clustering baseline
- PLDA + AHC
- VBx/HMM resegmentation
- cannot-link constraints from local segmentation
- temporal smoothing that is benchmark-gated and disabled unless it helps

Acceptance criteria:

- VBx can be enabled independently from neural segmentation.
- Resegmentation improves or preserves DER on at least two datasets before it becomes default.
- Bad smoothing experiments remain documented with benchmark evidence.

### 6. Overlap-Aware Result Schema

Add `DiarizationResultV2` rather than forcing all future output through single-speaker turns.

Required output:

- single-speaker turns for compatibility
- multi-speaker overlap turns
- frame-level optional score matrix
- confidence per turn
- speaker-count diagnostics
- source model/config metadata
- stable word-speaker assignment helper

Acceptance criteria:

- Existing `DiarizationResult` remains compatible.
- RTTM writing supports overlap-friendly output where the format allows multiple `SPEAKER` lines over the same time span.
- JSON output can represent multiple speakers per time span.

### 7. Streaming Diarization V2

`OnlineDiarizer` should evolve from sliding embedding clustering into a real low-latency diarization engine.

Required behavior:

- Rolling local segmentation buffer.
- Latency modes: 500ms, 1s, 2s, 5s.
- Speaker cache and centroid/PLDA state.
- Cannot-link constraints from simultaneous local speakers.
- Optional state carry-over across files/sessions.
- Incremental result revision policy: provisional vs final segments.

Acceptance criteria:

- Streaming output exposes `is_final` / `revision_id` semantics.
- Latency/DER tradeoff is benchmarked.
- WebSocket/server integration is possible without owning a Python runtime.

### 8. ASR and Word Alignment

Word assignment is a product-quality differentiator.

Required behavior:

- Assign speaker labels to words using midpoint, overlap-aware posterior integration, and confidence.
- Preserve ASR word timings.
- Return ambiguous speaker assignment when overlap or uncertainty is high.
- Support transcript-level relabeling after offline resegmentation.

Acceptance criteria:

- Word assignment has tests for boundary, overlap, and low-confidence cases.
- CLI can merge diarization JSON with word timestamp JSON.

## Non-Goals

- Training large neural models inside the Rust crate.
- Making GPU mandatory.
- Adding new runtime dependencies before benchmark evidence justifies them.
- Hiding model-license constraints.
- Chasing one dataset at the expense of reproducibility.

## ADR

Decision: Move polyvoice toward an overlap-aware neural + PLDA/VBx architecture while keeping the current VAD + embedding + clustering path as a lightweight baseline.

Drivers:

- Direct Rust competitors now claim pyannote-class pipelines.
- Current accuracy gap is structural, not just threshold tuning.
- Rust deployment remains the main product advantage.
- Public trust requires reproducible benchmarks.

Alternatives considered:

- Only tune AHC/spectral thresholds: insufficient against `speakrs`, pyannote, and `diarize`.
- Wrap pyannote directly: faster to good accuracy, but loses the no-Python/no-heavy-runtime advantage.
- Only integrate Sortformer: good streaming path, but limited speaker-count/general offline flexibility.

Consequences:

- More model metadata and benchmark infrastructure is required.
- Some features must be optional due model licensing and backend availability.
- The result schema must grow to represent overlap and diagnostics.

Follow-ups:

- Write the implementation plan.
- Split work into benchmark, segmentation, scoring, clustering, output schema, streaming, and packaging tracks.
