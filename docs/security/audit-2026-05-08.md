### Findings

#### SUPPLY-001: `paste` crate is unmaintained — LOW

- **Location:** `Cargo.lock` (transitive dependency).
- **Description:** `paste@1.0.15` is flagged by `RUSTSEC-2024-0436` as no longer maintained. It is a macro-procedural utility; no security vulnerability is known, but future bug fixes will not be provided.
- **Impact:** Low — no active vulnerability; potential future maintenance debt.
- **Recommendation:** Monitor `paste` usage. If it becomes a direct dependency, evaluate migrating to `pastey` or `with_builtin_macros` as recommended by the advisory.

#### SUPPLY-002: Model downloads rely on SHA-256 integrity but lack cryptographic authenticity — **FIXED**

- **Location:** `src/models/download.rs`, `src/models/manifest.toml`, `src/models/verify.rs`.
- **Status:** ✅ **Fixed (2026-05-09)**
- **Fix:** Implemented Minisign (Ed25519) model signing:
  - `minisign-verify` crate (zero dependencies, pure Rust) added under `download` feature.
  - Project public key baked into binary via `include_str!("signing.pub.base64")`.
  - Per-model signatures stored inline in `manifest.toml` as TOML multiline strings.
  - `download_with_checksum_and_signature` streams both SHA-256 and Minisign verification in the same 64 KB loop.
  - `download_with_checksum` preserved as backwards-compatible wrapper.
  - All 7 official models signed; `scripts/sign-models.sh` automates release signing.
  - CI `sign-manifest-dry-run` job validates manifest signature well-formedness on PRs.
  - `ModelEntry.signature` is `Option<String>` with `#[serde(default)]` — old binaries ignore it, new binaries fall back to SHA-256 when absent.

#### SUPPLY-003: `ureq` uses `native-tls` on some platforms — **FIXED**

- **Location:** `Cargo.toml`.
- **Status:** ✅ **Fixed (2026-05-09)**
- **Fix:** Changed `ureq` dependency to `ureq = { version = "3", default-features = false, features = ["rustls"], optional = true }`. `cargo tree | grep native-tls` returns empty. `rustls` is now the only TLS backend.

### Findings

#### FFI-001: `polyvoice_pipeline_run` trusts caller-provided `n_samples` without validation — **FIXED**

- **Location:** `src/ffi/mod.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** Added `const MAX_SAMPLES: usize = 16000 * 3600` (1 hour at 16 kHz). `polyvoice_pipeline_run` returns `PolyvoiceStatus::AudioTooLong` if `n_samples > MAX_SAMPLES` before creating the slice.

#### FFI-002: `models_cache_dir` accepts path-traversal sequences without sanitization — **FIXED**

- **Location:** `src/ffi/mod.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** `polyvoice_pipeline_create` rejects `models_cache_dir` strings containing `".."` before any filesystem operations, returning `PolyvoiceStatus::InvalidArg`.

#### FFI-003: Panics inside `destroy`/`free_string` are silently swallowed — **FIXED**

- **Location:** `src/ffi/mod.rs`.
- **Status:** ✅ **Fixed (2026-05-09)**
- **Fix:** Replaced `let _ = catch_unwind(...)` with conditional `eprintln!("polyvoice: panic during cleanup (foreign thread?)")` when `catch_unwind` returns `Err`. This provides observability without changing the C ABI (return type remains `void`).

## 3. Input Validation / DoS

#### DOS-001: v1.0 `Pipeline::run` lacks `max_duration_secs` guard — **FIXED**

- **Location:** `src/pipeline_v1/mod.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** Added `max_duration_secs` guard at the start of `pipeline_v1/mod.rs::run`, matching the legacy `Pipeline::run` behavior. Returns `PipelineError::AudioTooLong` if exceeded.

#### DOS-002: WAV parser has no file-size or duration limits — **FIXED**

- **Location:** `src/wav.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** `read_wav` now:
  1. Checks `std::fs::metadata(path)?.len()` against `MAX_WAV_FILE_SIZE = 1_073_741_824` bytes (1 GiB) before opening.
  2. Checks `reader.duration() / spec.sample_rate` against `3600.0` seconds (1 hour) before reading samples.
  3. Returns `WavError::FileTooLarge` or `WavError::DurationTooLong` respectively.
  4. Covered by `chaos_test.rs` (`read_wav_on_oversized_duration_header_returns_error`).

#### DOS-003: ONNX model files are loaded without structural validation — **FIXED**

- **Location:** `src/onnx.rs`, `src/ecapa.rs`, `src/silero_vad.rs`, `src/segmentation/powerset.rs`.
- **Status:** ✅ **Fixed (2026-05-09)**
- **Fix:** Added `validate_onnx_header(path)` in `src/onnx.rs` that reads the first 64 bytes and verifies either:
  1. ASCII `"ONNX"` magic in the first 16 bytes (some ONNX exporters include it), **or**
  2. First byte is `0x08` (protobuf wire-type tag for `ir_version` field), which all valid ONNX ModelProto files start with.
  Files smaller than 64 bytes are rejected. The function is called in every `commit_from_file` code path (`FbankOnnxExtractor::new`, `SileroVad::new`, `PowersetSegmenter::with_config`).
- **Note:** This is a lightweight header guard, not a full graph validator. Full structural validation would require parsing the entire protobuf model graph.

#### DOS-004: `PipelineConfig` default omits `max_duration_secs` entirely — **FIXED**

- **Location:** `src/pipeline_v1/config.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** Added `pub max_duration_secs: f32` to `PipelineConfig` with default `3600.0`.

## 4. Serialization Safety

#### SERIAL-001: RTTM parser accepts negative / NaN / infinite timestamps — **FIXED**

- **Location:** `src/rttm.rs`.
- **Status:** ✅ **Fixed (2026-05-08)**
- **Fix:** Added `is_finite() && >= 0.0` validation for both `start` and `duration` after parsing. Returns `RttmError::InvalidTimestamp` on violation.

#### SERIAL-002: JSON via FFI is safe but null-byte handling is implicit — LOW

- **Location:** `src/ffi/mod.rs:138–141`
- **Description:** `serde_json::to_string` produces valid UTF-8 JSON. `CString::new(json)` will fail if any string field contains a `\0` byte, returning `PolyvoiceStatus::Internal`. This is a graceful failure, not a memory-safety bug. However, an attacker who can influence speaker labels or turn text (if future versions add ASR text) could intentionally inject null bytes to force an Internal error.
- **Impact:** Low — graceful error, but potential DoS vector if user-controlled strings reach the JSON payload.
- **Recommendation:** Sanitize or strip null bytes from any user-influenced string fields before serialization, or use a JSON serializer that does not require `CString` (e.g., write directly to a pre-allocated buffer).
