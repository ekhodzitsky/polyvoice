| Severity | Count |

The codebase is generally well-hardened for a Rust project: `cargo audit` reports **zero known vulnerabilities**, all `unsafe` blocks in first-party code have SAFETY comments, and there are no hardcoded secrets. The main risks are (1) a missing DoS guard in the new v1.0 Pipeline, and (2) several input-validation gaps at the FFI and file-format boundaries that could allow resource exhaustion or path traversal when polyvoice is used as a library/service.

### Findings

#### SUPPLY-001: `paste` crate is unmaintained — LOW

- **Location:** `Cargo.lock` (transitive dependency).
- **Description:** `paste@1.0.15` is flagged by `RUSTSEC-2024-0436` as no longer maintained. It is a macro-procedural utility; no security vulnerability is known, but future bug fixes will not be provided.
- **Impact:** Low — no active vulnerability; potential future maintenance debt.
- **Recommendation:** Monitor `paste` usage. If it becomes a direct dependency, evaluate migrating to `pastey` or `with_builtin_macros` as recommended by the advisory.

#### SUPPLY-002: Model downloads rely on SHA-256 integrity but lack cryptographic authenticity — MEDIUM

- **Location:** `src/models/download.rs`, `src/models/manifest.toml`.
- **Description:** ONNX models are downloaded over HTTPS and verified against SHA-256 hashes embedded in `manifest.toml` (which is baked into the binary via `include_str!`). This provides **integrity** against network tampering, but not **authenticity**: if the machine that generated the manifest hashes is compromised, the attacker can ship a malicious model whose hash matches the manifest. There is no code-signing, PGP signature, or reproducible-build attestation on the model artifacts.
- **Impact:** Medium — an attacker who compromises the build/CI environment that generates `manifest.toml` can ship a malicious ONNX model that will pass SHA-256 verification and be loaded by `ort`. ONNX Runtime executes arbitrary compute graphs; a malicious model can potentially trigger memory-safety bugs in the underlying C++ runtime or cause denial of service.
- **Recommendation:**
  1. Sign model artifacts with a project-level offline signing key (e.g., minisign or PGP).
  2. Verify the signature in `download_with_checksum` **before** SHA-256 comparison.
  3. Publish the public verification key in-repo and document the key-rotation policy.

#### SUPPLY-003: `ureq` uses `native-tls` on some platforms — MEDIUM

- **Location:** `Cargo.lock` (`ureq 3.3.0` depends on `native-tls`).
- **Description:** While `ureq` v3 prefers `rustls`, the lockfile shows `native-tls` as a dependency, meaning platform-native TLS libraries (OpenSSL, SecureTransport, Schannel) may be used depending on feature resolution. Native TLS stacks have historically had more CVE surface than `rustls`.
- **Impact:** Medium — potential exposure to platform TLS library vulnerabilities; certificate validation behavior may vary by OS.
- **Recommendation:** Pin `ureq` to `rustls` explicitly in `Cargo.toml`:
  ```toml
  ureq = { version = "3", default-features = false, features = ["rustls"] }
  ```

### Findings

#### FFI-001: `polyvoice_pipeline_run` trusts caller-provided `n_samples` without validation — MEDIUM

- **Location:** `src/ffi.rs:126`
- **Description:** The function creates `std::slice::from_raw_parts(samples, n_samples)`. The doc comment states the caller must guarantee `samples` points to at least `n_samples` valid `f32` values, but there is no runtime check. A C caller passing a non-null `samples` pointer with a mismatched `n_samples` will cause an out-of-bounds read (information leak or crash).
- **Impact:** Medium — memory safety depends entirely on C caller correctness. This is standard for C FFI, but the lack of a defensive `n_samples` upper-bound check (e.g., against a reasonable maximum duration) increases risk.
- **Recommendation:** Add a defensive check:
  ```rust
  const MAX_SAMPLES: usize = 16000 * 3600; // 1 hour at 16 kHz
  if n_samples > MAX_SAMPLES {
      return Err(PolyvoiceStatus::AudioTooLong as c_int);
  }
  ```

#### FFI-002: `models_cache_dir` accepts path-traversal sequences without sanitization — MEDIUM

- **Location:** `src/ffi.rs:47–68`
- **Description:** `models_cache_dir` is passed directly from C to `ModelRegistry::with_cache_dir`, which calls `fs::create_dir_all` and uses the path as a base for downloading models. A malicious C caller could pass `"../../evil"`, causing model files to be written outside the intended cache directory.
- **Impact:** Medium — arbitrary file write in the user context; could be used to overwrite existing `.onnx` files elsewhere on the filesystem.
- **Recommendation:** Reject paths containing `..` components or resolve the path canonically and ensure it is within an allowed prefix.

#### FFI-003: Panics inside `destroy`/`free_string` are silently swallowed — LOW

- **Location:** `src/ffi.rs:163–171`, `src/ffi.rs:179–187`
- **Description:** Both `polyvoice_pipeline_destroy` and `polyvoice_free_string` wrap their `unsafe` blocks in `catch_unwind`, but the `Result` is discarded with `let _ =`. If a double-free or corrupted pointer causes a panic, the caller receives no error signal and may continue in an undefined state.
- **Impact:** Low — mitigated by the fact that well-behaved callers will not trigger this; primarily a debugging/observability issue.
- **Recommendation:** Return an error status code from `destroy`/`free_string` instead of swallowing the panic, or at minimum log the failure via `tracing`.

## 3. Input Validation / DoS

#### DOS-001: v1.0 `Pipeline::run` lacks `max_duration_secs` guard — HIGH

- **Location:** `src/pipeline_v1/mod.rs:90–93`
- **Description:** The legacy `pipeline.rs::run` enforces `config.max_duration_secs` (default 1 hour) before any processing. The new v1.0 `Pipeline::run` in `pipeline_v1/mod.rs` **only checks sample rate** and then immediately calls `self.segmenter.segment(samples)`. An attacker can pass an arbitrarily large audio buffer, causing unbounded memory allocation and CPU consumption during segmentation, embedding extraction, and clustering.
- **Impact:** High — trivial denial of service via a multi-hour audio buffer or a crafted large `Vec<f32>`.
- **Recommendation:** Port the `max_duration_secs` check from `pipeline.rs` into `pipeline_v1/mod.rs::run` before calling `segmenter.segment`.

#### DOS-002: WAV parser has no file-size or duration limits — MEDIUM

- **Location:** `src/wav.rs:17–45`
- **Description:** `read_wav` opens the file via `hound::WavReader::open` and immediately allocates a `Vec<f32>` for the entire audio content based on the WAV header. A malformed or crafted WAV file declaring a huge number of samples could cause an out-of-memory panic or excessive allocation before `hound` validates the actual file size. There is no upper-bound check on file size or duration.
- **Impact:** Medium — local/remote DoS via crafted WAV file when `run_from_wav` is used.
- **Recommendation:**
  1. Check `std::fs::metadata(path)?.len()` against a reasonable maximum (e.g., 1 GB) before opening.
  2. Or stream-read the WAV in chunks and fail if the declared duration exceeds `max_duration_secs`.

#### DOS-003: ONNX model files are loaded without structural validation — MEDIUM

- **Location:** `src/ecapa.rs:31–34`, `src/onnx.rs:32–35`, `src/silero_vad.rs:25–28`, `src/segmentation/powerset.rs:57–66`
- **Description:** All ONNX model loading paths call `ort::session::Session::builder()?.commit_from_file(path)` directly. There is no pre-validation of the ONNX protobuf structure, opset version, or operator whitelist. A corrupted or malicious ONNX file will be parsed by the C++ ONNX Runtime, which has had memory-safety CVEs in the past.
- **Impact:** Medium — if an attacker can place a malicious `.onnx` file in the cache or supply a custom model path, they can exploit vulnerabilities in the ONNX Runtime parser or executor.
- **Recommendation:**
  1. Keep `ort` updated aggressively.
  2. Consider adding an optional ONNX structural lint (e.g., `onnx-checker` equivalent in Rust) before calling `commit_from_file`.
  3. Run ONNX inference in a sandboxed process or with resource limits for untrusted deployments.

#### DOS-004: `PipelineConfig` default omits `max_duration_secs` entirely — MEDIUM

- **Location:** `src/pipeline_v1/config.rs:8–23`
- **Description:** The new `PipelineConfig` struct has no `max_duration_secs` field at all. Even if the caller wants to enforce a limit, there is no mechanism in the v1 API.
- **Impact:** Medium — API design gap that makes DoS prevention the caller's responsibility.
- **Recommendation:** Add `max_duration_secs: f32` (default 3600.0) to `PipelineConfig` and enforce it in `Pipeline::run`.

## 4. Serialization Safety

#### SERIAL-001: RTTM parser accepts negative / NaN / infinite timestamps — MEDIUM

- **Location:** `src/rttm.rs:53–61`
- **Description:** `parse_rttm` parses `start` and `duration` as `f64` via `.parse::<f64>()`. There is no validation that the values are finite, non-negative, or within a reasonable range. A malformed RTTM line with `NaN`, `-1.0`, or `1e308` could propagate through downstream code and cause panics in sorting, merging, or indexing logic.
- **Impact:** Medium — undefined behavior in downstream arithmetic; potential panics or logic errors in clustering/segment merging.
- **Recommendation:** Validate after parsing:
  ```rust
  if !start.is_finite() || start < 0.0 { return Err(...); }
  if !duration.is_finite() || duration < 0.0 { return Err(...); }
  ```

#### SERIAL-002: JSON via FFI is safe but null-byte handling is implicit — LOW

- **Location:** `src/ffi.rs:138–141`
- **Description:** `serde_json::to_string` produces valid UTF-8 JSON. `CString::new(json)` will fail if any string field contains a `\0` byte, returning `PolyvoiceStatus::Internal`. This is a graceful failure, not a memory-safety bug. However, an attacker who can influence speaker labels or turn text (if future versions add ASR text) could intentionally inject null bytes to force an Internal error.
- **Impact:** Low — graceful error, but potential DoS vector if user-controlled strings reach the JSON payload.
- **Recommendation:** Sanitize or strip null bytes from any user-influenced string fields before serialization, or use a JSON serializer that does not require `CString` (e.g., write directly to a pre-allocated buffer).

  ```
  *.key
  *.p8

  id_rsa.pub
  ```

## 6. Cache Integrity

#### CACHE-001: `ensure_in_cache_only` skips SHA-256 verification — MEDIUM

- **Location:** `src/models/mod.rs:143–158`
- **Description:** The `ensure_in_cache_only` method returns a cached file path without verifying its SHA-256. The comment explicitly says this is for tests, but the function is `pub` and not marked `#[doc(hidden)]` or `#[cfg(test)]`. If a production caller uses it, a file swapped by malware or another user on a shared machine will be loaded unchecked.
- **Impact:** Medium — loading of untrusted model bytes if the cache directory is writable by other principals.
- **Recommendation:**
  1. Either always verify the hash in `ensure_in_cache_only`, or
  2. Mark the function `#[doc(hidden)]` and document that it is test-only and skips verification.
